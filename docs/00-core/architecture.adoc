== Architecture

[.lead]
The Product Catalog service follows a *Hexagonal Architecture* (Ports & Adapters).
The domain core is framework-agnostic; Quarkus, JPA, and JAX-RS live at the edges.

=== Layering Rules

[cols="1,1,3",options="header",stripes=odd]
|===
|Layer |Package |Responsibility

|*API*
|`catalog.product.api`
|HTTP routing, request/response mapping, exception mappers.
No business logic. Delegates entirely to the application layer.

|*Application*
|`catalog.product.application`
|Use case orchestration. Validates intent, applies domain rules,
calls repositories, returns DTOs. No framework annotations except CDI.

|*Domain*
|`catalog.product.domain`
|The `Product` aggregate root. Pure Java — zero Quarkus, JPA, or REST imports.
The only place where business invariants live.

|*Infrastructure*
|`catalog.product.infrastructure`
|Persistence (`ProductEntity`, `ProductRepository`, `ProductMapper`),
REST client, filters. All outward-facing adapters.
|===

[IMPORTANT]
====
Dependency direction is enforced by ArchUnit on every build: +
`api → application → domain` and `infrastructure → domain`. +
The reverse is a build failure.
====

=== Key Design Decisions

[cols="1,3,3",options="header",stripes=odd]
|===
|Decision |Choice |Rationale

|ORM strategy
|Hibernate ORM + Panache active record
|Reduces boilerplate for CRUD while keeping the domain object (`Product`) clean

|Error contract
|Structured JSON error body, never raw exceptions
|Clients deserialise errors the same way they deserialise success; no string parsing

|Versioning
|URI versioning `/api/v1/...`
|Explicit, cacheable, and load-balancer friendly; no header negotiation complexity

|Test isolation
|Testcontainers PostgreSQL per test suite
|Real RDBMS semantics (constraints, transactions) vs. H2 approximation
|===
